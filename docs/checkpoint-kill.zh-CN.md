# 写检查点时终止进程，恢复会读到什么？

之前的[浏览器快照实验](crash-boundaries.md)只在导出前后终止进程。
[读者的后续建议](https://x.com/lastbrowser/status/2113390616713593177)是检查写入期间被终止的情况。
这次单独测试宿主的**检查点文件发布过程**，不把它混称为浏览器存储落盘测试。

当前源码在 macOS／Linux、Node 20 及以上可运行：

```sh
npm run demo:checkpoint-kill
```

此命令不需要安装依赖、浏览器、模型、凭据或服务。真实报告写入
`runs/checkpoint-kill.json`，结束后清理自己的临时目录。
使用当前源码或 v0.2.3。固定 v0.2.2 ZIP 不含此新增命令。

| 终止位置 | 之前已有检查点 | 新进程应读到 |
| --- | --- | --- |
| 直接覆盖文件、只写一半（反例） | 版本 1 | JSON 损坏，拒绝读取 |
| 临时文件只写一半 | 版本 1 | 完整、逐字节相同的版本 1 |
| 文件 fsync 完成、尚未 rename | 版本 1 | 完整、逐字节相同的版本 1 |
| rename 完成 | 版本 1 | 完整版本 2 |
| 临时文件只写一半 | 无 | 检查点缺失，不接受为恢复状态 |
| 文件 fsync 完成、尚未 rename | 无 | 检查点缺失，不接受为恢复状态 |
| rename 完成 | 无 | 完整版本 2 |

每一项都启动独立写进程，观察到指定文件边界后发送真实 `SIGKILL`，
确认退出信号，再启动另一 Node 进程读取。调用的是原有 `writeCheckpoint`
和 `readCheckpoint`；校验完整文件、校验和、任务身份、版本和操作账本。
遗留的 `.tmp` 文件只记录数量，不会自动提升成可恢复检查点。

旧版本含 `DISPATCHED`，新版本含 `CONFIRMED`。新进程用同一个操作标识、
新的动作标识尝试重放时，两种有效账本都必须阻止执行，持久化回调与目标调用
均为 0；文件损坏或缺失也不会授权重放。本实验不连接真实业务目标。

为精确复现，只有一次性写进程会拦截对应的 `node:fs` 调用：部分写入场景用
真实 `fs.writeSync` 写入序列化文件的一半，通过独立管道报告后等待终止；
另两项在真实 fsync／rename 返回后等待终止。正式写入器代码与接口未改动。
这不是随机打断操作系统写入调用，也不是浏览器 localStorage 刷盘、浏览器死亡、
远端业务提交、断电或恰好一次语义的证明。文件做了 fsync，父目录没有。

`npm test` 包含七项回归。Checks 工作流单独上传
`checkpoint-file-kill-evidence`，其中保留进程号、退出信号、实际接受的版本、
文件哈希和临时文件数量。请核对其真实提交和报告；通过仅覆盖表中的测试。
