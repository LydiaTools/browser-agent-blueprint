# 测试服务结束了，不等于所有 Node 进程都该结束

Agent 启动了一个预览服务。测试结束后，它看到另一个同名进程，准备清理。哪个才是这次任务启动的？

在一条 [Hacker News 讨论](https://news.ycombinator.com/item?id=50239041)中，一位开发者提到 Agent 清理同名 UI 进程时误结束了应用引擎；另一位提到进程匹配命令把自己也匹配了进去。这是个人反馈，不能据此推算问题发生频率。

这个示例验证一个更具体的做法：**同一个控制器启动两个配合退出的本地测试服务，通过启动时创建的独立通道关闭其中一个，再检查另一个仍能响应。**

```sh
npm run demo:owned-servers
```

需要 Node 20+，不需要浏览器、额外依赖、账号或模型。脚本启动两个全新的测试服务，让系统分配本机回环端口；确认两者可访问后，通知第一个服务关闭并等待正常退出，再检查它已无法访问、第二个仍然可用，最后关闭第二个服务。输出的 JSON 记录这些结果；每次端口和 PID 可能不同。

控制器只通过创建子进程时获得的 IPC 通道发送退出请求，子进程自己关闭 HTTP 服务。示例不会按名称、端口、PID 或路径查找或发送结束信号；IPC 断开时子进程也会尝试关闭。操作对象仅限本次启动的两个合成测试服务。

## 使用范围

这不是通用进程清理工具或操作系统安全边界。真实服务需要配合实现退出协议；任意已有进程不会自动支持。子进程可能忽略请求、保留连接、启动脱离管理的后代或意外退出。控制器失去句柄后，此示例无法重新识别和恢复此前的进程；它也无法阻止拥有独立 Shell 权限的 Agent 结束其他进程。真实宿主需要自行适配、测试和实施进程管理。

[proc](https://github.com/yazeed/proc) 提供端口／进程查询和预览操作；[AgentDust](https://github.com/hamzahamidi/agentdust) 描述了在支持环境下按会话清理进程的方案。这些是独立项目，尚未在此进行基准比较或集成。

v0.2.5 源码包和当前源码包含本示例；固定的 v0.2.4 ZIP 发布于示例加入之前。
